# 时间线系统审查报告

## 审查范围

本次审查覆盖：

- 剧本节点是否完整；
- 场景跳转和分支边是否与实际脚本一致；
- 章节归类是否正确；
- 节点缩略图和预览图是否对应正确场景；
- 缩略图缓存是否会过期或读错资源；
- 中文文字解码、字体路径和预览文字是否正常；
- 时间线的缩放、拖动、点击、键盘操作和翻页；
- 图表布局、章节可读性和当前节点提示。

当前 `cargo test --release` 的 68 个测试全部通过，但现有测试主要验证不崩溃、节点不重叠、缩略图有输出和缩放数学正确，不能证明章节标签和每个节点的语义一定正确。因此本报告把“测试通过”和“内容正确”分开评价。

## 结论分级

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P0 | 310x/320x 的 CODA 雪菜线与和纱线标签反了 | 用户会把两个结局分支认错 |
| P0 | 2020–2033 被标成“终章·雪菜”，实际仍属于 CC 共通线 | 章节边界错误 |
| P0 | 中文预览使用普通 SJIS 解码和位图字 | 中文模式预览可能出现伪日文、缺字或字体风格不一致 |
| P1 | 5000–5104 被拆成“序章特典/终章特典”，项目已有数据把它们视为电子小说 | 额外章节归类错误 |
| P1 | 缩略图选择“全场景最少共享图片”，不保证是场景开头或代表画面 | 缩略图可能来自后段 CG，节点看起来像别的场景 |
| P1 | timeline 缓存不检查源素材时间戳或哈希 | 更新素材后仍显示旧缩略图 |
| P1 | 图表没有画章节列、章节边界或路线标题 | 用户无法快速理解分支结构 |
| P1 | 分支节点没有明确标记选择点，边也没有分支语义 | 2019 等关键分叉不够直观 |
| P2 | 键盘上下键按“全图最近车道”跳转，可能跳到不相邻路线 | 操作结果不可预测 |
| P2 | 缩放和拖动是连续的，但缺少重置视图、回到当前节点和路线筛选 | 长图浏览成本高 |
| P2 | 预览文字使用旧位图字，和时间线标题的矢量字不统一 | 界面文字系统不一致 |

## 一、节点和分支的正确性

### 已确认正确的部分

当前实现把带下划线的子剧本折叠到入口场景，例如 `1008_020` 归入 `1008`。对于“时间线按可进入场景展示”的目标，这个取舍是合理的，否则图表会出现大量玩家无法直接选择的内部节点。

现有测试也确认了：

- IC、CC、各角色路线和 CODA 节点能被收集；
- `2019` 至少连接到 `2020、2301、2401、2501` 四个分支；
- 子剧本不会单独占据图表节点；
- 节点不会落在同一个 `(col, lane)` 单元格。

### 仍然需要补强的部分

`script_jumps` 只识别 `Op::Act { id: 0 }` 当前记录里的最后一个 `Tok`，再把符合数字格式的 token 当作脚本跳转。这个规则对于目前已知的 CATCH 跳转能够工作，但它没有输出：

- 跳转来自哪个选择项；
- 这是普通顺序跳转、选择跳转还是 CATCH/CATCH2/CATCH3；
- 目标是否是同一入口的子脚本；
- 目标是否存在对应 `.bnr/.txt`；
- 某个场景是否存在多个互斥的跳转条件。

因此当前图只能表达“静态上可能连接”，不能表达“玩家选择哪一项后会走哪条边”。建议为节点增加：

```text
has_choice
jump_kind
choice_targets
unreachable_reason
```

边增加：

```text
kind = sequential | choice | catch | conditional
label = 选项文字或 CATCH 名称
```

对于 `2019` 这样的关键分支，应在节点右上角显示分支标记，并给四条边使用不同颜色或短标签。否则用户只看到四条线，很难确认哪条是小春、千晶、麻理/雪菜或共通线。

### 必须增加的图一致性检查

建议增加一个离线检查命令，输出以下内容：

```text
节点总数、每章节点数
没有入边的节点
没有出边且不是结局的节点
脚本跳转到不存在的目标
脚本存在但没有被任何入口收集的节点
同一入口折叠了多少子脚本
所有分支节点及目标列表
```

“没有入边”不一定是错误，因为 IC、CC 和额外小说可能是合法入口；但应显式标为 `root`，不要让它们看起来像丢失的边。

## 二、章节归类存在明确错误

`lane_chapter` 当前的映射和项目已有的路线数据不一致：

```text
3100..3111 => Coda · 和纱
3200..3211 => Coda · 雪菜
```

项目中的路线数据和场景命名显示，实际应为：

```text
3100..3111 => CODA · 雪菜
3200..3211 => CODA · 和纱
```

另外：

```text
2020..2033 => 终章 · 雪菜
```

这批场景在已有流程数据中仍属于 `CC-共通`，不应单独归入雪菜线。`2025` 也不应通过特殊分支单独变成“终章·雪菜”，除非有明确的原版路线资料证明它是独立结局节点。

额外电子小说目前被映射为：

```text
5000..5004 => 序章特典
5100..5104 => 终章特典
```

项目内已有的路线数据将 5000–5104 统一归类为“电子小说”。如果产品希望将其拆成两个章节，应该在数据表中明确写出，而不是在 `lane_chapter` 里隐式猜测。

建议不要继续使用数字区间直接推断章节。改成静态、可审查的数据表：

```text
IC              1001..1013
CC-共通         2001..2033
CC-小春         2301..2322
CC-千晶         2401..2413
CC-麻理/雪菜    2501..2517
CODA            3001..3024
CODA-雪菜       3101..3111
CODA-和纱       3201..3211
CODA-EXTRA      3901..3909
电子小说        5000..5004、5100..5104
```

更稳妥的做法是建立 `timeline_chapters.tsv` 或 Rust 常量表，并让测试逐个断言关键节点：

```text
3101 == CODA-雪菜
3201 == CODA-和纱
2020 == CC-共通
5000 == 电子小说
5100 == 电子小说
```

## 三、缩略图选择逻辑不够语义化

当前 `scene_files_with` 的策略是：

1. 收集场景所有背景和 CG；
2. 解析这些图片；
3. 统计每张图片被多少场景共享；
4. 选择“被最少场景共享”的图片；
5. 如果同分，优先 CG，再按脚本中的出现顺序。

这个算法能减少很多节点都显示同一张开场背景的问题，但它不保证图片是该场景的代表画面。例如一个场景先显示房间背景，后面出现一张只在本场景出现的事件 CG，当前算法会优先选择那张后段 CG。用户点开节点时看到的缩略图就会和场景入口不一致。

建议将图片选择拆成两个概念：

```text
entry_shot       场景进入后第一张有效背景/CG
representative   用于时间线展示的代表图
```

推荐选择顺序：

1. 场景真正执行到的第一张有效 `ACT146/147/148` 图片；
2. 如果只是重复上一场景背景，则选择场景内第一次发生变化的图片；
3. 如果场景没有新图片，沿用入口背景，但标记为 `inherited`；
4. 只有用户明确选择“代表图模式”时，才考虑后段事件 CG。

同时保存来源信息：

```text
shot_kind = entry | changed | inherited | event_cg
shot_op_index
source_script
source_variant
```

这样可以在调试模式中显示“该缩略图来自哪个 ACT 和哪一个脚本文件”，方便逐场核对。

## 四、缩略图缓存存在过期问题

`load_thumbs` 只检查：

```text
data/cache/timeline/<stem>.tga 是否存在
```

它不检查缓存是否比源文件旧。`tools/build_timeline_cache.py` 也只要目标文件存在就跳过。因此当 8x WebP 更新、替换或重新生成后，时间线仍可能读取旧缩略图。

建议至少比较：

```text
cache.mtime >= source.mtime
```

更可靠的是生成清单：

```text
data/cache/timeline/manifest.tsv
stem  source_path  source_size  source_mtime  source_sha256  width  height
```

运行时只在清单匹配时使用缓存。没有匹配时：

- 若允许后台生成，先显示占位图并异步生成；
- 若要求立即正确，重新生成该节点的 320×180 缩略图；
- 不要直接为一个 104×58 节点解码完整 8x WebP。

当前 `data/cache/timeline` 中已有大量缩略图，但内容更新后必须重新运行：

```bash
python3 tools/build_timeline_cache.py --force
```

## 五、缩略图来源和解码路径

正常路径使用 `tv*` 缩略图是正确方向：节点只有 104×58，预览约 208×117，没有必要解码完整 CG。

但缓存缺失时，`load_thumbs` 使用 `decode_ui_file(&path)` 作为回退。场景图不是 UI 图，长期方案应改为：

```text
优先 timeline cache
→ 其次 tv* 原始小图
→ 再其次 artcache 的目标倍率图
→ 最后才是 decode_art_file
```

UI 解码器适合 `sys_*`、标题图和指令条等逻辑尺寸贴图，不应成为场景 CG 的通用回退路径。

另外，节点图和预览图的宽高比例并不完全一致：

```text
节点：104×58
预览：208×117
```

预览是 16:9，而节点比例略有偏差。建议统一为 16:9，例如 `104×58` 改成 `104×59`，或节点使用 `106×60` 后留边框，避免每个节点都有轻微压缩。

缩略图质量方面，当前流程是“320×180 缓存 → 再 fit 到节点/预览”。这比直接拉伸 104×58 好，但应保证只缩放一次或使用统一的高质量缩放函数。节点小图适合面积平均；预览图适合 Lanczos 或双线性，二者不必共享同一采样策略。

## 六、中文文字系统目前不完整

这是时间线中最明确的文字问题。

### 1. 预览正文没有使用中文补丁解码

`run` 通过 `preview_line(script_dir, &chart.nodes[sel].id)` 读取文本，而 `preview_line` 内部固定调用：

```rust
sjis::decode(&bytes)
```

中文模式使用的是 `script_cn/`，其文本是 CK-GAL 的伪日文 Shift-JIS 编码，应使用项目已有的中文转换路径 `sjis::decode_cn`。否则预览文字可能是日文假名/伪汉字，而不是用户在正文中看到的中文。

建议把语言模式传入时间线：

```rust
pub fn run(..., cn: bool) -> Option<String>
```

然后：

```rust
let text = if cn {
    sjis::decode_cn(&bytes)
} else {
    sjis::decode(&bytes)
};
```

不要通过目录名猜语言。

### 2. 预览正文仍使用位图字体

时间线标题、提示和章节标签使用 `text_label` 的矢量字体，但场景预览引用使用：

```rust
font.draw_pitch(&mut s, quote, ...)
```

这会让预览区域出现“标题是矢量字、正文是旧位图字”的混合效果。中文模式下还可能因 cell map 覆盖率不足而缺字或字形风格不一致。

建议把预览引用改成和正文相同的 `VectorFont` 样式：

- 使用 SC face；
- 预览字号 18~22 逻辑像素；
- 不使用对白正文的粗黑描边；
- 对长句做两行截断；
- 在预览区域内按实际 ink bounding box 排版。

日文模式可以保留位图字体，但中文模式必须走矢量字。

### 3. 章节标签不应只拼接字符串

当前预览标题是：

```text
chapter + "    " + scene_id
```

建议拆成两个视觉元素：

```text
chapter badge     CC 共通线
scene id          2019
```

这样可以分别控制字重、颜色和间距，也不会因章节名称长度不同导致场景号跳动。

## 七、时间线视觉安排需要重做信息层级

当前 `paint` 主要绘制：

- 连接线；
- 节点缩略图；
- 选中/悬停边框；
- 顶部 banner；
- 底部预览条。

但 `Node.chapter` 没有在图表区域显示，章节只出现在底部选中节点的文字里。因此图表虽然有多条 lane，用户看不到每条路线的含义，也看不到章节边界。

建议加入以下视觉层：

```text
chapter bands       章节列或路线背景带
chapter headers     IC、CC 共通、小春、千晶、CODA 等标题
route lanes         主线、各角色线、额外小说
branch markers      选择节点和 CATCH 节点标记
current marker      当前存档位置
```

建议颜色只用于表达路线，不要让每张缩略图边框都使用不同颜色。可以采用：

- 主线：冷青；
- 小春：暖绿；
- 千晶：橙色；
- 麻理/雪菜：紫色；
- CODA：金色；
- 电子小说：灰蓝。

节点本身保持较低饱和度，选中节点使用金色粗边框，分支节点额外显示小圆点或分叉图标。

章节标题应固定在图表顶部或左侧，不随节点缩放消失。缩放时标题和章节边界可以保持屏幕像素大小，节点和连线才随世界坐标缩放。

## 八、连接线和分支表达

当前连接线从节点右侧直接用 elbow 连到目标左侧。对于同列或相邻列的多条边，可能出现：

- 多条线重合；
- 线穿过其他节点；
- 分支目标没有箭头方向；
- 远距离边和普通顺序边看起来一样。

建议：

- 普通顺序边使用细暗线；
- 选择边使用亮色或虚线；
- CATCH 跳转使用箭头和标签；
- 线段进入节点前留出 6~10 像素间隙；
- 多条边在分叉处使用共享干线，再分别弯向目标；
- 对跨章节的边画成更明显的曲线或带标签的跳线。

不要只靠“选择节点后看底部预览”来理解分支。图表本身应该能说明哪里分叉、分到哪条路线。

## 九、交互审查

### 当前可用的操作

- 鼠标滚轮缩放；
- 鼠标拖动平移；
- 点击节点选择；
- 再次点击或按确认键进入场景；
- 方向键在同一 lane 或相邻 lane 中移动；
- 右下角分页按钮平移图表；
- 点击底部预览图进入当前场景。

### 当前操作上的问题

`step_lane` 根据全图中 lane 距离和列距离选择最近节点，不保证目标是当前节点的父节点、子节点或视觉上相邻的节点。分支路线较长时，按上/下可能直接跳到另一条路线远处的节点。

建议键盘操作改为：

1. 左右键优先沿当前节点的 `prev/next` 图边移动；
2. 没有相邻边时，再选择同 lane 最近节点；
3. 上下键选择与当前 x 区域最近的其他 lane 节点；
4. 如果存在多个候选，优先同一章节和同一分支；
5. 目标改变后保持节点在安全区域内，不要大幅跳屏。

建议增加这些操作：

```text
Home       回到故事起点
End        跳到当前路线末端
F          回到当前存档节点
R          重置缩放和滚动
Tab        在章节之间切换
1~9        选择可见章节
Esc/右键   返回标题或关闭时间线
```

分页箭头目前按固定屏幕宽度移动，适合横向图表，但没有显示页码或当前视口。建议增加小型 minimap 或章节进度条，让用户知道自己在整张时间线的哪个位置。

点击节点时最好有两阶段反馈：先选中并刷新预览，再次点击或按确认进入。当前点击一个非选中节点只改变选择，点击选中节点才进入，这个规则应在提示文字中明确写出。

## 十、推荐实施顺序

1. **先修章节映射**：310/320、2020–2033、5000/5100，并增加逐节点测试。
2. **修正中文预览**：传入 `cn`，调用 `decode_cn`，改为矢量字体。
3. **修正缩略图缓存有效性**：增加源文件时间戳或 manifest 校验。
4. **改缩略图选择**：记录 entry shot，优先场景入口画面，不再单纯按共享次数选择。
5. **增加图表章节层**：章节标题、列背景、路线分组和分支标记。
6. **重做键盘导航**：优先沿图边移动，再按空间邻近回退。
7. **改善连接线**：箭头、分支样式、跨章节跳转和避让节点。
8. **最后调整缩放和分页体验**：重置视图、当前节点、minimap 和章节跳转。

## 最终判断

当前时间线的基础框架可用，节点收集、四分支检测、缓存缩略图和拖动缩放都有基础实现，68 个测试也说明底层交互没有明显崩溃问题。但“章节对不对”和“预览文字是否正常”目前还不能判定为完成：章节映射有明确错误，中文预览文字路径也没有接入中文解码与矢量字体。

最先应修正的是章节和文字，再修正缩略图的语义选择，最后改善章节可视化和键盘导航。否则用户会看到一个能点的图，但无法可靠地判断自己正在选择哪条路线、哪一章以及该节点实际从哪一张画面开始。
